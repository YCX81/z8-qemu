# Z8 C3.11 视频信息层旋转：当前进展与历史原型

## 当前范围

目标为视频取景／录制信息支持左右竖拍、主 MENU 保持原厂行为，以及独立的[录像文件方向记录](z8-video-file-orientation.md)。用户提供的两张参考图来自 ZR；这里只参考其视频控件组织，不移植 ZR 的屏幕比例或像素位置。界面尺寸、原始字体和图标来自 Z8 C3.11 本身。当前仍是私有 QEMU 研究，未完成真正录制、文件或真机验收。

新增 `build_plan(..., video=True, video_portrait=True)` 与 `UnlockedGuest(..., unlock_video=True, video_portrait=True)`。它们与旧 `video_layout=True` 整体缩放方案互斥：使用原厂 `480×720` 竖向画布，只过滤视频抑制位 `1`，保留主菜单位 `20` 和自动旋转设置。不会强制把尺寸 getter 改回横向。

本轮从原始 `403a65a0` 的控件描述读取和实际源画布追踪确认：共享拍摄控件表 `43a21a70..43a2c53c` 中，有 274 个非空横向矩形对应空的竖向字段。新代码补齐这些字段，已有竖向字段及横向字段保持原值。文本和图标矩形保持原宽高；快门、ISO、音频分段等组合控件按组移动，避免数字、标签、外框彼此挤压。宽提示控件居中。坐标是本项目编排的实验布局，不是恢复出的原厂视频竖屏设计。

该表是共享拍摄资源，因此现有验证范围是默认照片页面和已捕获的视频显示组合；没有宣称覆盖所有照片信息显示组合。源矩形、修改范围、原始／替换摘要均记录在派生镜像清单中，不写入原 MAIN。代码继续使用原厂渲染器；宿主不旋转最终截图。

## 当前运行证据

2026-10-14 的接续结果见[录制链路排查](z8-video-pipeline.md)和本地 `progress3.json`。本轮解除 C0/C1 停止确认的超时，接入普通文件虚拟卡及实际写入后的源通知，但仍存在下游等待，未通过完整录制或稳定回切。以下 `progress2.json` 属于前一轮证据；其“空介质”描述不能用于已明确启用新虚拟卡的运行。

私有证据仍在 `.local/analysis/video-osd-20261013/`，本轮汇总为 `progress2.json`。`native06` 曾在短流程中显示照片左竖拍、视频左右竖拍和照片右竖拍；它使用较早的布局和模型，不代表当前完整切换通过。当前 `final-ui05` 已显示左右视频信息，但录像键操作后的长时间往返出现原厂 **“Error. Turn camera off and then on again.”** 提示。照片／视频完整、稳定往返仍未通过，模式字节正确或短暂出现照片画面不足以替代这项验收。

当前 `menu-stock01` 与 `menu-patched01` 使用相同 QEMU 构建，分别加载原 MAIN 和当前 UI 派生 MAIN；两者都等待完整菜单像素后再截图。视频左竖拍时主 MENU 的 RGB SHA256 均为 `eade74774105b43ae8aa550800f4854db6cc4288f55a6293f6fae9c5d31036e5`，逐像素差异为 0，主菜单位为 `20`。两次运行均无错误并正常清理。该结果证明已测主 MENU 保持原厂画面，不能代表录像后的错误流程也已恢复。

`combined02` 显式组合文件矩阵实验，加载后核对全部 277 个修改区间；左右视频信息与右竖拍主菜单均完成显示。主菜单像素仍匹配上述基线，运行无错误并正常结束。该运行没有触发真正录像对象创建，不能替代文件实验的函数级测试或真实录像验收。

文字已摆脱上一版整体缩放，电平控件显示为完整的一组，不再是三个重复条带。原始 `40c83950` 会按采样打包方式右移 8 或 16 位，再由 `40c839cc` 取字节映射到 14 档；先前 65536 / 1073741824 试值因此不能可靠驱动峰值。`tests/test_z8_video_audio.py` 验证两种打包方式下，0 映射 0 档、`007f7f00` 映射 14 档。

`audio-menu01` 已通过实际接口输入的 **0→14→0**：源画布电平区域有 1120 像素变化，最终 LCD 区域有 3168 像素变化，归零后两处 RGB 哈希分别与初始区域完全相同，未留下残影。该证据是合成输入经原厂换算与渲染的显示验证，不代表真实麦克风、PCM 录音或音画同步验证。该运行的菜单截图仍是上一帧取景画面，菜单结论只使用上述独立完整像素对照。

预览曾显示为只剩局部内容，原始 PNG 的完整 RGB 哈希核对表明对应前后帧完全相同，不能据此认定界面消失。

`native05` 和后续流程确实送达两次录像键输入，但画面仍有不可录像标记。现有默认模型为空 SD／PCIe 介质，新增视频接口模型也没有编码数据生产者。**按键送达不作为录制开始／停止、计时、文件关闭或可播放视频的通过证据。**

## 本轮恢复的控制路径

以下均受 `z8-video-interface-model=on` 限定，默认入口不启用。它们补足控制、配置或空管线停止行为，不实现音频采样、视频编码或真实硬件时序。

| 原厂路径 | 本轮模型 |
|---|---|
| `40c20338`、`40c30bf8` | 第二接口 `15300000/15b00000` 的独立配置、复位 ID `15`，以及请求／确认位 `200000` |
| `40cc4920` / `40cc4a44` | 共享接口复位 ID `27` 的释放／断言，独立清理所属配置和缓冲地址 |
| `40c71848`、`40c748b8` | `15648000` 配置域、独立参数银行及两组 36 位缓冲地址；状态和编码数据仍严格限制 |
| `40cb8e20` | `15432000` 视频通道按原厂两路地址／行检查配置；照片通道仍要求原有八路 |
| `40cbe568` | `d154150/d154030` 的时钟配置提交；同步锁存是假设，不是视频帧完成 |
| `40c24404/18/2c` | 三个已观察的 1→0 任务控制脉冲，仅记录控制边沿 |
| `40c1fc78`、`40c1f8b8` | 视频几何通道 `4000/8000` 的停止命令、原因位、ISR 复位及确认；与像素完成分开 |
| `40c18050` | 没有 FIFO／DMA 生产者时的空传输状态，仍不提供采样或 FIFO 数据 |

重复往返还暴露了 LCD 模型的独立问题：原厂回切时暂时关闭信息叠加层，使用 `1024×576` 的 NV12 直通源在 `1024×682` 画布的 `(0,54)` 位置显示。旧模型要求叠加层开启且直通尺寸等于整个画布，导致真实像素读取和帧结束通知停止，源画布已变为照片而 LCD 仍保留旧视频画面。显式视频模型现在支持有界的直通窗口和可选叠加层；只有实际读取到有效源才产生显示帧，越界或没有有效源不产生帧。该偏移解释是仿真中的功能模型，未验证物理面板时序。

持续运行曾在 `41170d84` 因外部参数索引 16 为 0 而下溢，随后错误转储读取未知寄存器。新增 `z8_video_resources.attach_processing_index()` 仅在外部 ROM `47f5af50` 提供记录号 1，沿用既有中性记录假设。原厂系数没有恢复；没有修改最终方向、模式、故障返回值或录像状态。这一输入必须明确启用，其来源和限制写入运行记录。

完整 Python 回归通过 373 项，优化模式下 34 项重点测试通过；本轮相关六个 Python 模块的行覆盖率约 94%，既有 C 像素测试也通过。设备测试及构建身份以本地 `progress2.json` 为准。当前视频设备／像素测试 63 项，菜单像素回归 9 项，旋转采样回归 12 项，均使用同一最终构建。上述结果不构成真机可安装功能，没有提交、推送或刷机。

## 前一轮历史原型

以下保留先前整体缩放方案的范围和失败记录；它仍可显式运行，但不作为当前 `video_portrait=True` 的布局说明。

2026-10-13 的目标改为：照片／视频模式切换后，视频取景和录制信息支持左右竖拍，主菜单维持原厂横向。此前的视频文件类型菜单实验不作为这条流程的通过证据。

目前已获得左右竖拍的视频信息层**初次显示原型**，并保留主菜单的原厂禁止位。它采用原生整体等比适配，文字比照片竖拍小，音频电平区域仍有刷新残影。**这不是与照片模式等效的最终布局，也没有通过持续视频取景、实际录制启停或完整模式往返验收。**

## 已实现的范围

- `tools/z8_video.py` 提供 `input_body('photo'|'video', key)`。每个按下和释放包均保留选择器状态；`key` 可为 `None`、`record`、`half`、`menu`。
- 原始 `41020844` 解码器将包 `0x57` 字节送到抽象输入的 `+0x26` 半字；录像键在包 `9` 字节，对应 SW1 `0x2000`，原厂标记为 `ID_SW1_MOVIE`。Unicorn 执行原始解码器验证映射；未写入拍摄模式变量。
- `build_plan(..., video=True, video_layout=True)` 和 `UnlockedGuest(..., unlock_video=True, video_layout=True)` 显式选择视频布局。该选项拒绝同时解锁主菜单。
- 保留视频 `0x1` 作为原生横向逻辑布局标记，仅有效显示方向、通知和禁止状态忽略它。共享尺寸 getter 只在该标记有效且原尺寸为 `480×720` 时转换为 `720×480`。主菜单 `0x20`、其他禁止位及自动旋转关闭仍有效。
- 六处身份校验范围共 156 字节；无新增可执行映射、堆或额外栈空间。原始 MAIN 保持不变，仅生成私有派生 MAIN，不生成升级包。

新增参数不会改变旧菜单实验的默认参数或派生镜像字节。单独的 `video=True` 仍只过滤策略位，不能解决视频信息层裁切。

## 仿真模型与输入边界

视频模式首次进入了照片路径未覆盖的设备初始化。新增模型均需要显式的 `z8-video-interface-model=on`，默认启动路径不启用它。

| 原生证据 | 当前实现 | 尚未实现 |
|---|---|---|
| `40c178bc` 与 serial5 门控函数 | 配置 `+10/+40/+44`、请求门控锁存 | FIFO、音频 DMA、采样或完成事件 |
| `40c18308` / `40c182b8` | 通道 0 的 `+54/+58/+5c/+60` 读取显式四字输入 | 物理含义、标定和音频采样验证 |
| `40c2073c..40c208dc`、`40c204dc..40c206a8` | `150d9800` / `150d9a00` 两个独立几何配置块及 `4000/8000` 提交 | 像素处理、处理结果和完成事件 |
| `40c314ec`、表 `4164c494` | 复位 ID1 的精确请求对 | 有在途数据时的真实硬件复位行为 |
| `40c315d0..40c31984` | `152c0000` 配置与空 pending 的确认 | 视频数据处理及处理后缓冲状态 |
| `40c31988..40c31a48` | `15ac0000` 配置，记录只写表端口输入 | 表解释、编码输出或完成中断 |

诊断使用 `z8-video-serial-input=0:0:0:0` 明确供给四个原始读回值。它们不是从相机采集的声音，也不能作为录音或录制成功证据。输入经过整组校验后才更新；不提供默认有效读回值。

## 当前运行证据和失败点

私有记录位于 `.local/analysis/video-osd-20261013/`；`progress.json` 为本轮分层结果，`final-left01` / `final-right01` 为最终构建的运行记录。`layout02` / `layout03` 是先前构建的诊断，保留原始截图与失败，不混称最终验收。

在真正的选择器输入后，原生 UI 模式字节变为 `01`，显示视频编码格式、帧率和音频控件。左右方向由 I2C 输入经原厂分类得到；主菜单方向锁与照片回切逻辑均未用宿主状态写入替代。原型截图中的色条来自既有合成 RAW 夹具；静止色条不能单独证明视频取景持续运行。

持续运行或返回照片时仍可触发：

```text
Z9_UNKNOWN cpu=0 pc=0x40c1fbb0 write addr=0x150c0010 size=4 value=0x200000
```

这是另一条视频引擎控制请求。`40cae7d0..40cae7ec → 40c202f4` 进一步选择复位 ID `0x15`；尚未恢复该设备完整行为，因此仍由严格模型拒绝。没有跳过原生调用、吞掉未知访问或强制制造完成位。

现有机型配置另外只模拟空 SD 卡槽和空 PCIe 存储。录像键的原生解码、MCU 收取及屏幕快照均不等同于录像开始／结束。没有验证录制计时、编码数据、落盘文件或可播放视频。

接续工作依次为：恢复该视频引擎的控制及数据路径，修复音频电平区域的刷新和真正的竖向布局，再用可录制介质完成启动、停止、文件关闭及照片／视频往返。现有源代码和运行证据均不构成真机可安装功能。

## 验证

本轮 351 项 Python 测试通过；30 项方向相关测试在 `python -O` 下通过。23 项视频模型 QTest 检查覆盖字段、配置隔离、提交顺序、显式输入及拒绝边界。它们不替代上述未完成的界面和录制流程。

私有仿真仍显式启用方向资源、`z8-secondary-resample-model=on`、视频接口模型和读回输入。完整输入身份、QEMU 身份、截图像素哈希、每次运行错误和进程清理状态以 `progress.json` 及运行目录为准。
