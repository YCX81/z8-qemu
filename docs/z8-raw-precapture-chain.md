# Z8 RAW 预拍：原固件条件调用链与验证缺口

分析日期：2026-10-12。对象为本项目持有的 Z8 C3.11 MAIN。本文记录原固件静态分析；没有修改 RAW 路由、制作更新镜像或刷机，也没有把 host 生成的 RAW/NEF 当作机身拍摄结果。

**结论：已定位从 HSFC 历史队列提交，经后端阶段调度、RAW 输出记录、NEF 容器和文件系统，到具体介质写入口的条件链。尚未证明实际高速预拍帧具备该链要求的 Bayer 数据、格式状态与缓冲所有权，因此不能称 RAW 预拍已实现。**

## 2. S：实际输入回调、历史保留与提交

任务构造 `0x40f6b7a0` 以 cfg ID `0x10035` 创建 HSFCPROC 的通用消息任务；`0x40f6ba50` 是事件回调，直接 OS 任务入口是通用循环 `0x40c00264`，不能混称。

原初始化在 `0x40f6bd14` 调 `0x40e9c9d8`，把 `0x40f6e4a0` 注册到 `0xa03b83858`。前端工作完成回调 `0x40ea0298` 在正常分支经 `0x40ea048c..0x40ea04a4` 发出事件 `0x04120040`，x1 为原 capture job，随后进入上述 HSFC 回调和 `0x40f6eb64`。

另一路 LVENC 的 `0x40e993a0` 也会发 `0x04120040`，但 payload 是报告结构，`+0x1f0` 才是原 job 指针，走另一组回调。**相同事件数值不足以证明 payload 或调用链相同。**

通过原有检查的 capture job 由 `+0x44` 状态决定历史行为：0为清理路径，1为保留路径，2为提交历史及当前帧路径。其他字段如 `+0x10/+0x1b/+0x48` 会影响进入条件。保留队列位于 `0xa03bc1e08`，mutex 位于 `0xa03bc193c`。

| 操作 | 关键位置 | 已核实行为 |
|---|---|---|
| 保留上限 | `0x40f6ff94 → 0x40f96d70` | 读取 `0xa03bc6bac` 的当前数量上限，必要时弹出最老项 |
| 追加 | `0x40f6fff0 → 0x40c7a410` | 追加外层对象指针 |
| 提交历史 | `0x40f6fe90 → 0x40f93098` | 按出队顺序提交，写 metadata+0x120 的序号 |
| 提交当前 | `0x40f6ff38 → 0x40f93098` | 历史提交后处理当前对象 |
| 丢弃/归还 | `0x40f7bb18 → 0x40e9cd74` 等 | 释放关联资源、metadata 和外层对象，并更新计数 |

真实保留数量来源是 `0x02001c11 → 0x40ec44e4 → 0x40f9a488 → 0xa03bc6bac` 的配置链。mode3/4/5/6分别有 `[9,15,30]`、`[36,60,120]`、`[18,30,60]`、`[5,8,15]` 的配置表；将其解释为特定帧率下的0.3/0.5/1秒窗口属于数值对应推断，不能替代模式实值观测。

队列预分配120个24-byte节点，但无空闲节点时可再分配。**120不是120张RAW像素内存，更不是硬性帧容量。**

## 3. S：对象/像素缓冲契约与转换反例

历史构造 `0x40f6f900 → 0x40f74f14` 分配 `0x1230` bytes 外层对象，清零 `+8` 开始的 `0x1228` bytes，再单独分配 metadata，存于外层 `+0x790`。这两个大小不能拿来计算 RAW 帧缓存。

在 `0x40f6f968`，原 input+0x9e0 指向的信息经 `0x41059214` 转换到新 metadata。`0x40f6f9d0..0x40f6f9e4` 显式继承：

```text
input job +0xd8  → history outer +0x688
input job +0xe0  → history outer +0x748
```

原 producer `0x40e8c200..0x40e8c218` 令 input+0xd8 指向 input 内嵌的+0x788 descriptor，并调用 `0x4104521c(info,pool=0xa03b6c3b8,descriptor)`。这个函数从实际固件池取条目、调用池回调，填写 buffer record、像素地址和索引；不是 host 生成帧。

RAW step 的入口有另外的硬条件：

```text
metadata +0x294 必须满足 0x41059014 的条件（值0或1）
metadata +0x286c == 0 时：outer +0x3f0 必须非空
metadata +0x286c != 0 时：使用 outer +0x3a0 的 descriptor
```

具体在 `0x40eabd10..0x40eabd4c`，输入传给下游的是相关 descriptor+0x30。历史构造没有直接继承 `+0x3a0/+0x3f0`，所以改格式枚举或服务 ID 并不自动满足 RAW 输入条件。

同时存在必须保留的反例：矩阵 `0xa02acc138` 的 `[0,1]` 阶段前两步为 `0x40ea8ee8/0x40ea8fc8`。前者分配 outer+0x3a0，后者把 outer+0x748 的 descriptor 字段作为输入、+0x3a0字段作为输出，经 `0x40ea90e0 → 0x40e891c0` 处理并等待完成，随后归还+0x748。因此不能仅以构造处指针不同断言不存在可复用转换路径。

该矩阵由 metadata首word==3 或 outer+0x10==3 的条件选取。**D：尚未确认实际高速预拍使用此模式，也未确认+0x748中的格式和该转换器可接受的 bit depth。** input+0xd8被JPEG helper消费，也不等于它自身已是JPEG压缩数据。

## 4. S：真实后端调度与JPEG/RAW条件分支

历史提交进入 `0x40f93098 → 0x40e9ca98/0x40e9caa0`。后端分配 work `0x4e8`：work[0]指向pipeline context，context+0x18指向外层对象，work+0x4e0为完成回调`0x40ea2224`。

`0x40e9cb4c → 0x40ea26b8(outer)` 选择阶段矩阵，`0x40e9cb58` 将其存于work+8。队列consumer `0x40e9af9c` 经 `0x40e9afd0 → 0x40d16950` 调度；scheduler检查11×15矩阵和依赖，向node+8任务对象投递`0x430d0001`。通用handler`0x40d17368`从node+0x28序列逐项调用真实步骤函数。

默认表`0xa02ac8bf0`同时含Bayer、resize、JPEG、RAW、TAG、REC等阶段。已核实的14个后端表共195个非空节点、103个不同步骤地址；另解析18个前端表。**这是已选取的静态表集合，不是全部执行过的路径，也不证明HSFC必然用默认表。**

矩阵选择还读取metadata的+4/+5/+6/+0x71/+0x74/+0x75/+0x9c/+0xa0/+0xb0/+0xb8/+0xe8/+0x12e/+0x12f/+0x13f、首word及outer+0x10。实际矩阵必须记录。

| 条件支路 | 已核实调用链 | 不能外推的结论 |
|---|---|---|
| 主JPEG helper | STGJPEGA/B首步`0x40eaeed8/0x40eaeefc → 0x40eaea0c → 0x40eaeb8c → 0x40e82090 → 0x40e82208 → 0x40c9b648` | 不是由HSFCPROC任务名直接绑定JPEG |
| RAW/附图有关的JPEG helper | 第二步骤经`0x40eaf398 → 0x40eaf554 → 0x40e82090` | 此函数允许RAW条件；命中JPEG不等于JPEG-only，附图具体用途仍属I |
| RAW descriptor枚举<=2 | STGRAWA/B→`0x40eabcd0 → 0x40eabda0 → 0x40e84b68 → 0x40e85028 → 0x40cb53b8` | 接到了命名RawService的真实API，但不能给整个模块统一命名为NEF编码器 |
| 上支路相应失败且枚举!=2 | `0x40eabdc8 → 0x40e850ac`，清meta+0x2a4 | 未为fallback算法定名 |
| RAW descriptor枚举>2 | `0x40eabe88 → 0x40e89618 → 0x40cbef1c` | 是另一驱动入口，未仅凭枚举猜压缩标准 |

格式状态方面，`0x41059460/0x41059468`将**实际传入信息**+0x3c8复制到metadata+0x294；`0x41059484/0x4105948c`把+0x3d8复制到metadata+0x2fc。JPEG谓词`0x4105903c`允许+0x294∈{0,3}且+0x2fc!=1，另一谓词`0x41059068`处理+0x2fc==1的对应条件。

已排除一个误连候选：`0x40f3cc84`也写某对象+0x3c8，其上游配置ID为`0x06001729`，但对象身份未与上述info闭合；名字/ID候选表反而提示`LimitSelectableImageArea_16to9`。因此不能据相同offset把它宣称为RAW/JPEG格式开关。

## 5. S：NEF容器、文件服务和介质写入口

这里的NEF身份超出了服务字符串：`0x4086cd48`从fileID得到低四位类型（15映射14）；`0x4086dabc`的表`0x44187118`将type2分派至`0x4086db0c`，返回`0x44187184`的ASCII `NEF`。实际文件名路径`0x408694bc/0x408694c0`使用该类型及扩展名。

RAW输出结构在outer+0x6a8，相关descriptor位于该结构+0x58。STGTAG `0x40eb16a0`遍历pipeline context+0xc0起的输出项（每项0x2d8、数量+0xbc），调用`0x40eb17e0`。它对filetype2走`0x40eb192c`，将**同一output-record+0x58**写入entry[0]，并组装其他段；`0x40eb1a98`返回容器format1。这是RAW输出记录与明确NEF类型之间的静态桥。

`0x40eb17b0 → 0x406cc130 → 0x406c31bc`组装header/分段。STGREC `0x40eb1f1c`通过原任务`0xa03b853b0`的event1唤醒`0x40ea340c → 0x40ea3478`。filetype映射表`0xa029d67b0`将NEF type2映为format1，`0x40ea3638 → 0x406cc134 → 0x406cd308`执行写入。

writer处理format1的9段，取得文件对象、打开文件，逐段分块调用`0x406cd62c → 0x406ce07c → 0x406ce108 → 0x4085b9a0`；再处理最终长度和关闭/释放。**S证明此代码路径存在；D尚缺其输入像素有效、每段长度正确和最终NEF可解码证据。**

```text
4085b9a0 → 4085b89c → 402db28c
  → File I/O command 0x1d（normal与fast均通向402dbc34）
  → 402dc094 投递 0x420a1001
  → 402dc778 worker → 402dd78c（默认后端）
  → 408b6db8 文件系统写 → 408be474 卷写回调
```

卷+0x28的回调通过真实mount链注册，来源为原设备描述表`0x41f18248`：

| 固件名字 | 注册的block write | 下一级 |
|---|---|---|
| SD | `0x402df1fc` | `0x402df280 → 0x40291e74`，按driver状态继续`0x402a1404`或`0x40298638` |
| XQD | `0x402dfc48` | `0x402dfca0 → 0x402713f8`，经实际注册函数表转`0x4027174c → 0x402a6d40`或`0x40271894 → 0x40270b5c` |

本文保留固件的XQD名字，没有凭此断定实际卡协议。I/O worker另有通过`[0xa02e81a00]`的替代后端；此表未声称覆盖该分支。写函数存在不等于卡命令完成、持久化或错误恢复已验证；本项目的实验NAND持久化也不是这条SD/XQD NEF链的替代证据。

## 6. I / D：为什么不是“只改JPEG路由”或“30fps完全富余”

**I：**目前可合理判断预拍改造有可复用的原后端，但具体做法依赖实际帧格式、模式和所有权。阶段矩阵、谓词、输入descriptor、输出记录、完成回调和回收契约共同决定能否进入NEF链。JPEG与RawService的request ABI并不相同；还有第三条RAW输出驱动路径，因此替换服务ID无法满足完整契约。

**D：**没有对实际高速预拍的像素、位深、压缩输出大小、队列占用、DMA重叠、卡速、丢帧或热负载进行测量。不能用“已有RAW视频”直接证明14-bit静态NEF流水线的吞吐；12-bit RAW视频、14-bit静态RAW、不同分辨率的高速模式必须分别观测。

量级演算只能给需求：若假设8256×5504像素、14-bit紧凑打包，则每帧按`8256×5504×14/8`计算；若以16-bit存放，则按`8256×5504×2`计算。这些是假设输入布局的算式，均未计stride、额外平面、处理读写、双缓冲、预览/附图与压缩工作区，也不等于NEF文件写卡率。缓存应按实际分配器的每帧字节数和同时在途帧数核算，不能只数链表节点；公式本身不提供带宽余量证据。

需要分别证明：传感器/ISP生成匹配输入、半按期间保留且不提前回收、全按时历史顺序正确、RAW/NEF输出正确、媒体完成、退出/失败时资源归还，最后才评估目标fps与窗口。

验收分层：

1. 普通NEF单张实际经过上述writer，并得到可独立解码、尺寸/位深/帧ID一致的输出。
2. 已有JPEG预拍实际保留/提交顺序和buffer寿命可复现；找出与普通NEF的实值差异。
3. 证明高速路径保有或能安全增持匹配Bayer输入，再设计最小实验改动；当前不做该改动。
4. 成功的小窗口RAW历史输出、取消/卡满/失败路径资源平衡之后，再去掉停机断点测fps、延迟、背压、实际峰值内存和卡速。

当前尚未完成第1项，不能用静态表解析计数替代。
