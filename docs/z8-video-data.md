## 协调交接后的协议修正

已按本地 `MESSAGE-TO-ORIENTATION.md` 和只读仲裁调整分工：本树为唯一视频 MMIO/IRQ 集成者，保留 WLVR/WLYV/Wave5；C1 提供协议和反例。交接前 83 个未提交源码文件已备份，检查点为 `.local/checkpoints/video-protocol-handoff-20261014T070540Z`，当时无本会话运行中的 QEMU。没有合并或覆盖 main，也没有提交、推送或刷机。

移植的是行为和测试，不是第二套设备后端：152c/1530 DATA 为 `0x3`，最后一个 DATA 位 W1C 才退休；第三槽 DATA 退休后独立请求 REFILL `0x10`；STOP END 为 `0x4`。两端分别锁存完整、重新提交的双 bank，并验证 decoder 的 `+534` 容量和几何。C1 的完整新提交授权 C0 缓冲复用，半表、仅 selector 和旧有效位都不能代替提交。原 `40c31610/40c30e60` 的 held local flush 保留 stream proof 至随后的 STOP；SoC reset 则取消本端未确认 END，不记成功 ACK。

`protocol-handoff-green03` 的五组协议检查通过，覆盖上述规则、原序列的 local flush、独立 reset 取消，以及前端和 C1 的 0→1→0。RAW 完整性、实际 YUV→HEVC、C0 selector 不变但 alternate 完整重写的回归分别通过；这不等于全部合并/ABA 反例已经完成。

在**不加方向补丁的原 MAIN**、`ring-repeat` 关闭的对照中，`protocol-original-native02` 的原 receiver/decoder client 分别收到 DATA3 21/20 次，REFILL16 各5次；`protocol-original-native03` 又观察到 decoder END1/ACK1。三轮原 MAIN 对照均有独立卡审计和解码：分别6/7/7帧 HEVC 3840×2160，但仍无 MOV／MP4，停止输入后仍显示 REC。它们不能与历史派生固件18帧当作吞吐对比。

另有独立、默认关闭的 `z8-video-source-end-model`。原 `40e9671c` 在计数3时等待 `0x80800000`；关闭时四次返回0。`protocol-source-end-native01` 开启后，实际图像写入后的 source0 bit29 获得5次原 ACK，四次等待均返回1，独立码流解码7帧，卡仍无录像。设备测试覆盖第三个真实输出、DATA ACK不代替 END ACK、reset取消。该通知与前端 END4、REFILL16和 C0/C1 ring-stop 分别计数；分组时刻仍是明确的功能模型，物理时序未证明。

`ring-repeat` 仍不作为验收基线。后续需闭合 guest STOP、drain、mux、文件关闭，以及迟到 consumer／地址 ABA／reset 中 job 的反例；已有包内 epoch 检查不能替代这些验证。

第四路预检现按仲裁补齐：每个平面分别要求唯一、启用的 alias 映射，验证通道控制、B3 启用、容量及八路输出与输入 RAW 包的互斥。在写任何输出之前拒绝这些配置错误。`test_z8_video_fourth_safety.py` 的13例覆盖单平面重复 alias、缺失/屏蔽/未启用映射、双平面/预览/输入重叠、压缩容量不足，以及两个合法交易。早期夹具把 C0 的32位寄存器误作64位写入，已纠正并加入未知 MMIO 检查；早期失败不全是设备缺陷。

YUV DMA 在交接时暂缓，原红例保存在 `.local/deferred/yuv-dma-red-20261014.py`。完成上述协议阶段后，`protocol-drain-native01` 观察到30个实际编码帧和原编码结束命令，随后停在 `40c19164 → 15680010`：channel4、mode0、YUV alias `200000000` 向 `8bc4ab200` 读取。后续原寄存器快照及 `40ca6298/62c8`、`40c19024/34/4c` 明确了字段：`+1c/+20` 是源／目标行距，`+24` 是复制宽度。因此实际为 **128×64 小块、双端行距3840**，早先将 `+20` 当宽度的解释和相应设备用例已被反例纠正。

默认关闭的 `z8-yuv-dma-model` 仅处理该 channel4/5 mode0 YUV 读取，先验证实际 WLYV RAM 的元数据与内容，再写目标。DMA可读取编码器消费后仍留在RAM中的有效图像，不从encoder队列取走owner；缓存每次先重新读取并逐字节比较包头和完整压缩载荷，相同才复用解包结果。`protocol-yuv-dma-stride-green01` 使用每行不同的像素，验证源位置、目标padding、未ACK不可覆盖、缓存内容变化与坏CRC拒绝。尚不能据组件测试宣称原生文件已经关闭。

`protocol-dma-native03` 和 `protocol-a1-observe01` 已实际完成2040次矩形 DMA，共12,441,600字节，即完整3840×2160 NV12。缓存命中2038次，DMA拒绝为零；读取的是保存在RAM中的第10代首帧。前者编码缓冲区独立解出30帧4K HEVC，末尾有单独7字节结束单元的 FFmpeg 提示；虚拟卡 fsck 返回0，但 `movie_files=[]`。这仍是编码缓冲区证据，不是原生容器。

随后原 `40cb84cc → 40c27244` 请求 A1 `15421104=3801`，输入来自上述真实 DMA 目标。默认关闭的 `z8-yuv-single-model` 仅接受现场确定的两种单次内存处理配置：A1 NV12到B2/B3/B4的1/2、1、1/6尺寸NV16；A2 NV16到B4的1/4尺寸NV16，支持目标行padding。它先检查全部输入/输出跨度、读取输入，再产生像素并写RAM，最后发布原 `40cb7154` 消费的A域bit4。没有替原任务写flag，也不为空作业发成功。最近邻缩放是声明的功能替代，不是恢复的尼康滤波算法；其他格式/模式仍严格拒绝。

`protocol-a1-native01` 已越过 A1：一项作业读取12,441,600字节、实际写出三路21,196,800字节，原程序继续请求A2的640×360→160×90处理；当时A2尚未支持，卡仍无MOV/MP4。

## 已执行的原录制路径

原 MCU 录像键已被接收，但此前被日期状态禁止。给 MCU family7 提供明确的模拟 RTC 状态后，原 `DtTm_MX1` 发布 `43100003`，原函数自行清除禁止项 `0x25`，进入 `40f75940`。没有写就绪位或修改函数返回值。`tools/z8_rtc.py` 记录外部输入来源。

真正录制又访问了外部处理索引的 selector10。`attach_processing_index(recording=True)` 只增加这一项的中性诊断记录；默认 selector16 不变。这些替代资源不是恢复出的工厂校准。

录制输入要求 8280×4688、14 bit RAW；原预览容量边界不够。功能模型现通过实际 WLVR/zlib 包 RAM 传输并校验这一尺寸，设备测试独立解包比对了 38,816,640 个样本，无差异。输入来自声明的合成 Bayer 源，并非真实 CMOS 采集。

## 编码前的实际图像数据

参考固定版本 [ZR f9cc5d1](https://github.com/WonderLantern/zr-qemu/tree/f9cc5d1f0c7dc06c275a08c16f668c6eb087869b)，补齐接收器／解码器所有权、ISP0/C1、源 channel13，以及 NR 配置与复位。原处理器对真实数据完成分别执行 W1C；各阶段有独立所有权和取消计数。

原录制 A1 从 `0x202` 切到 `0xa02`，除三路预览外启用第四路 B3/F3 4K 输出。仅凭预先保留的 B3 参数不能认定通道已经启用。第四路 C0 描述符使用 YUV 虚拟地址，`1564` 写端与 `1566` 读端的虚拟别名可能不同，必须通过两块实际物理缓冲匹配一帧。

`z8-yuv-data-model` 默认关闭。开启后，第四路把实际已解码 RAW 的简化 ISP 输出写为有尺寸、代次、长度、CRC 的 WLYV/zlib 包，保存在原程序分配的 RAM 中。编码器端重新读取这些字节，检查双平面与代次，并拒绝损坏数据。虚拟别名重配保留已完成的物理包；显式复位或实际新 DMA 覆盖分别记为取消，不冒充读取或上游确认。WLYV 是仿真内部替代格式，不是尼康 YUV 压缩。
