## 当前 Z8 的实际位置

**2026-10-14 编码路径更正：**RAW57 的 `D[0]=0` 实际选择固定长度传输，
不是无损压缩。即使模型在该请求内写入 F0，原程序仍使用固定 U16 长度，
且省略 MakerNote `0x96` 压缩头；该原型的组件测试不能作为原生 NEF 证据。
错误地接纳传输请求的 F0 原型未用于原固件运行。RAW58 已改用 `D[0]=1`，
用旧冻结模型实测取得压缩请求：`1540+44=0`、`+40=0x10000`、
`+D4=22,841,728`，并记录完整的15项 Huffman 码字和长度表。
同一暂停态确认输出格式5、4140×2756、输入格式4/行距8288；此轮实测
metadata `2a8=0`。RAW IFD 位深回调读 `D+4`，不能据 `2a8` 单独判断位深。
RAW 预留容量取实际记录 `record+50=68,712,960`，并核对所属分配的范围；
`1540+D4` 是这次输入占用量，不是输出容量。

更新至 RAW63 完成、153c 合并准备检查点：**第一张历史 RAW 已由原程序写入
卡内 NEF，LibRaw 全部11,409,840个样本零差异，三张附图均可解码；
多张保存、完整资源生命周期及预拍摄窗口仍未通过。**

下面保留较早的诊断过程，便于追踪原阻塞及其修复。

已经在仿真 RAM 中证明保留的 pre-FULL 帧，以及原固件从历史地址选择数据，
随后进行配对解码和两路中性 NR。RAW46b 完成输入和接收器 END，原生等待

NZ8BAYR1 的压缩传输本身无损，但早期原固件请求的解码目标是6240字节行距、
4140×2756。实验模型对它采用 packed12，并执行14→12四舍五入转换。
因此早期解码链路**不是端到端无损**。上述 U16 路线已经消除此转换，旧配置
仍保留为独立兼容路径。不能通过改变最终文件的 BitDepth、
回填宿主缓存或给旧帧重新加标签消除这个缺口。

RAW48c 已实际选中 HSFC 后端表 `a02acc138`，并观察到原生 NR API 返回0。
随后两次 MIPU 准备都从 RAW 侧输出分配函数返回空，阶段返回1并重试，

   预测初值，编码流34,339,053字节，LibRaw0.22.1独立解码45,705,600个样本
