# RAW 预拍：时序输入与格式政策对照

更新至2026年10月13日。以下均为固定 Z8 C3.11 在本地 QEMU 中的有界实验。**普通触发后 NEF 已通过独立解码及完整像素比对；触发前历史帧闭环仍未完成**。原 MAIN 保持不变；只有标明的C15政策对照运行独立派生程序，未生成更新容器或刷机。

## 普通 RAW 的等待计数

原 RAW + Lossless 菜单与触发路径已经实跑。此前并非停在 CCOMP 应答：原应答、GPIO、任务转发及 flag8 路径均继续执行。真正的大等待数来自原时序计算，不能靠强制完成或跳转消除。

负对照 C09 在原 `0x41172528` 直接取得：系数 W20=0，除法分子600599、分母600600、完整商0。分母非零，也不是商的低16位溢出。随后同一输入对象的 `+0x128/+0x12e` 变为65535，上游加1得到 `acb0=65536`，最终约5.4万次等待。

实际输入为 mode0、`+0x174=1`、sub3。原选择函数因此取表索引1；原资源0x5c已搬至RAM `0xa155d78c0`，读系数的相对位置为 `0xe3022`。原仿真只补充了索引0和13的sub3系数，缺少索引1。

正对照 C10 仅新增一个外部ROM表项：`0x47f63022` 的16位值为1200。该值沿用现有虚拟行时序假设，**不是恢复的原厂校准**。原读取现场实际核对了 selector1、sub3、X21=`0xa156ba8e2`，以及ROM和搬运后RAM均为1200；没有改实时RAM或固件算术。

| 原运行数值 | 缺表项 C09 | 单表项对照 C10 |
|---|---:|---:|
| W20时序系数 | 0 | 1200 |
| 除法分子 / 分母 | 600599 / 600600 | 3464999 / 600600 |
| 原完整商 | 0 | 5 |
| 输入半字+0x128 | 65535 | 4 |
| 原acb0 | 65536 | 5 |
| 原CSEQ计数 | 约54300 | 5，初始剩余4 |

修复这项仿真输入后，原流程跨过旧调度卡点，首个新未知访问为 CPU1 在 `0x40c1784c` 读取 `0x0e200110`。原调用者 `0x40c7d1b4` 调用串行外设配置函数；该函数对偏移+0x10的高2位、+0x40的bit8和+0x48的低16位做读改写，不是完成等待环。现有模型尚未保持这三个配置字段。未知访问返回的占位0不是硬件复位值证据，也不能用它声明通信完成。

C10在首个未知访问后停止；单张传感器请求、RAW151和JPEG后处理仍为0，没有NEF。此结果证明时序输入修正有效，未证明整个拍摄完成。

## C11：普通 NEF 正对照

此轮使用原MAIN，原UI关闭快门声音、选择RAW与Lossless，并保持正常S模式。外部时序系数为上述1200，同时显式开启[有限串行配置模型](z8-serial5-config.md)。137个接点及返回全部匹配，程序正常退出、独占QEMU关闭，原输入和驱动哈希未变；拍后恢复实时取景。

从停止的虚拟卡完整导出 `DCIM/100NCZ_8/DSC_0001.NEF`，文件80790528字节，SHA-256为 `d3a59913fecf887036ba88aa6f4c3abccdfaa80b9577adca3629f9816201959a`。目录与exFAT检查通过，没有由宿主生成或替换NEF。

- rawpy0.27.1 / LibRaw0.22.1解码得到8280×5520个14位样本；**全部45,705,600个样本与实际D980/RAW151快照一致，差异0，帧ID1及反码正确**。
- NEF的RAW strip共80,017,920字节，连同行padding与实际RAW151 packed输出哈希相同。
- 三个内嵌JPEG分别为160×120、8256×5504、1620×1080，均可解码；本轮没有保存独立JPEG编码器完整快照，不宣称该层逐字节比较。
- 原RAW步骤、NEF tag和writer均实际到达，writer返回0；251个NVMe请求、1141条事件、190次普通写入全部完成并交付CQ，无失败或挂起。NEF整个卡范围均被writer调用后的成功写入覆盖。

完整数值与证据界线见[单文件收据](verification/raw-single-20261012.json)。实际DMA时间为190696949981ns，晚于原GPIO全按处理190664648640ns和MCU全按消费190664851288ns，因此是**触发后帧**。两条触发路线都记录，未证明其中一条是唯一触发者。

单帧外设模型的requests/frames仍为0，这帧由已启用的周期stream模型提供；不能把有效NEF外推成单帧硬件协议验证。原pool分配和完整缓冲寿命、逐文件writer对象身份、多帧保留/顺序仍未闭合。该组合对照也没有分别证明关闭声音与配置模型各自是否充分；稀疏音频观察点未命中不代表全运行从未有音频活动。菜单的Lossless选择和功能性packed14输出，不等于真实尼康压缩或ISP算法已恢复。

## C12：公开工具及更小的普通 RAW 条件

后续 `capture-public-12` 使用公开probe与资源guard、默认capture profile、同一不可变二进制，**不启用串行配置保持选项**，仍经原UI关闭快门声并选择RAW+Lossless。137个接点和返回全匹配，原时序LDRH实际读出1200，原输入和监视源码未变，正常退出且独占QEMU停止。

虚拟卡再次写出1个80,790,528字节NEF（SHA-256 `51f11c113bb7198d924679a5c9e07cc204ac3cd2ead69bf652d7382893b3b458`）。LibRaw解码的45,705,600个样本零差异，完整80,017,920字节RAW strip与实际packed缓冲相同，三个内嵌JPEG可解码。251请求/1141事件中190次普通写入全部完成，文件范围有writer调用后的写完成覆盖。

原GPIO和MCU FULL消费分别为190361806177ns、190361875003ns；DMA完成190376346981ns，仍是触发后帧。该对照证明此公开配方不需要新增串行配置选项；没有证明所有声音模式或音频外设已实现，也没有新增历史帧、逐writer对象、完整缓冲寿命或拍后LCD视觉验收。完整命令见[公开普通RAW配方](z8-capture-resources.md)，数值见[单文件收据](verification/raw-single-20261012.json)中的 `public_cli_control`。

## C15 预拍的资源与缓冲

原UI已选择C15、d3预拍窗口0.3秒，实际释放模式6、容量5。HALF-only负对照02的原处理模式14经原表映射到资源索引槽15；缺项0经32位减1形成越界。直接异常PC=`0x41170d84`、FAR=`0x2a156b2806`、ESR=`0x96000005`，保存的寻址寄存器与原指令精确闭合。

对照03仅在外部ROM `0x47f5af4f` 补1字节记录号1。原LDRB实测为1，原读取基址回到有效资源对象，旧下溢消除。记录1依旧是已有中性仿真输入假设，32字节记录未修改、系数未恢复。

随后原固件写 `0x150c0008=0xff00` 被现有D980模型拒绝。掩码本身合法；实际配置目标是内部流端口 `0xe0000000`，不是已分配的RAM。D980同时使用控制+0x118=3和高度低16位2，与当前普通RAW内存写入模型不同。没有将内部端口映成RAM，也没有放宽校验或制造像素完成。

## NEF 政策与早期数据流

对照04在03基础上仅改独立程序副本的一条4字节政策指令：`0x40edec78` 强制选择格式1。实验期间它影响全部格式候选，**不是最终的C15专用开关**。20组Unicorn对照确认仅目标格式寄存器改变，其它通用寄存器、条件标志和PC一致。这些指令测试不计为拍摄验收。

```text
原 MAIN SHA-256
2b43a31c9de838f84b12416de4348a7004e65be07f853ec56ec2b10f3a8e3853
实际执行的政策副本 SHA-256
fb11ccb2ae3fb27931cfcf3bc0ab90f11b37757cb8222dfcbf20b40258c8ee25
```

原绑定仍从原MAIN核对，实际kernel路径、派生hash和政策差异另行记录；不是运行时改PC、任务标志或完成结果。所有原/派生文件前后hash一致，独占QEMU已停止。

| 现场字段 | 原JPEG政策03 | 强制NEF政策04 |
|---|---|---|
| 格式候选 / 有效门控 / 结果 | 3 / 0 / 3 | 3 / 0 / 1 |
| 实际拍摄info+0x3c8 | 本次未直接采样 | 1，已直接读取 |
| D980源路线 | 内部FIFO | route mode11，四槽仍为内部FIFO |
| D980完成帧 / 历史队列暂停样本 | 0 / 52次均空 | 0 / 52次均空 |
| 首个未知访问 | `0x150c0008=0xff00` | 相同 |

原生产链也说明这不是丢失了一个RAM指针：`0x40e8d794` 按job+0x10的类型11选择helper ID0x26，随后 `0x40eb60e8 → 0x40eb68e4` 明确构造内部端口并写入request+0x140四个源地址。这个源地址生成分支没有Bayer RAM分配或引用计数；这不代表整个下游没有其它RAM生产者。格式1已进入info，却没有改变这条job类型与源路线。

本实验在尚未建模的内部流启动处就已停止，**尚未证明RAW输出或历史缓存成立**。它不能排除内部Bayer流的下游原consumer会分配RAW输出，也不能据此判断在完整硬件模型或实体相机中是否只需修改门控。本项目还须追到内部流消费者、有效RAM输出、保留、转换、提交及释放。

## HALF06：越过内部启动，停在组合停止协议

默认关闭的[内部流启动模型](z8-d980-internal.md)仅接受已观察的28字配置和0xff00启动，32项实际QTest通过。HALF06保留05的RAW/Lossless、C15、0.3秒窗口、私有格式政策副本与资源输入，未发送FULL；它实际接受内部启动，随后在原PC `0x40c1fce4` 写 `0x150c000c=0xf04f` 时严格停止。95次原输入消费及返回匹配，104次队列暂停样本仍为空，D980/RAW输出/标记均为0。

首故障之后、所有CPU真正暂停之前，还发生原独立stop0x10；启动日志active=0xff5f与最终暂停态active=0xff4f属于不同时间，不能互换。新增取得的152处理器配置只见内部端口及较小的几何字段，未发现可据以认定历史Bayer的RAM输出。该控制模型不产生内部像素、帧完成或来源通知；启动通过不能计为预拍成功。

## HALF07/08：定向取消、控制退休和释放后的资源缺项

HALF07保持启动模型不变，只增加有界被动观察。实际0xff00经 `0x40caddbc → 0x40cadb54` 同步路径返回；停止入口 `0x40caeddc` 的LR为 `0x40caeb0c`，其前置helper返回1且输出token为1。原代码证明该token来自按消息对象登记的定向取消记录；更上层仍有多个caller，不能仅凭这些记录认定超时或模式切换。已有active服务会直接调用当前request回调，绕过两槽订阅表；表中没有HSFC回调不能单独证明通知缺失。

HALF08仅切换到[独立F04F停止模型](z8-primary-f04f-stop.md)并增加其只读状态。原request、hold、kick、ISR、reset及ACK已完整退休，requests/kicks/acks=1，owned=0。96次接点消费与返回全匹配，没有FULL；107次有界队列样本仍为空，没有D980/RAW/标记像素输出。原与派生输入、87个源文件哈希保持一致，自有进程退出。

新异常在半按释放之后：原释放消费137531964116ns，资源查询138430522394ns。实际输入mode2经原表选择slot3，加载后的RAM单元 `0xa156b2803` 为0，原LDRB也返回0；32位减1后在 `0x41170d84` 形成FAR=`0x2a156b2806`、ESR=`0x96000005`。slot15仍为1。按已定位的资源映射，对应外部ROM候选单元为 `0x47f5af43`，但本轮未直接读取该ROM字节，也没有填入新值。

此时还观察到第二次D980提交：8280×5520、pitch14496、control118=3、四个内部端口；latched仍为0，尚未启用。它不是第二帧或新的RAW输出，当前精确4140配置模型未因此放宽。未来单字节record1对照只能检验退出阶段的索引恢复，不能替代内部像素供应、历史保留或真实校准。

## 剩余验收

1. 普通Z8 NEF正对照已通过；继续取得实际allocator、逐job身份和缓冲寿命证据，不把周期源结果当作历史帧。
2. 为高速路径确定内部Bayer流消费者、实际RAM输出和所有权，不先假设必须由D980直接写RAM；保留历史期间不得提前复用，不能以内部端口地址替代像素快照。
3. 关联同一帧的格式、历史队列、RAW后处理、NEF writer及实际NVMe写入。
4. 至少两帧触发前历史加一帧触发后，核对全部文件的时间、FIFO顺序、数量和LibRaw解码的完整像素，再检验取消与重复拍摄的释放行为。

两项外部资源现有[显式实验选项](z8-capture-resources.md)，公开接入已过契约测试，不能自动沿用原私有运行的动态验证。独立NEF政策副本仍为私有研究配方。另有默认关闭的[串行配置保持模型](z8-serial5-config.md)，仅覆盖已确认字段。工具与限制见[诊断驱动](z8-capture-probe.md)、[多帧审核器](z8-precapture-audit.md)和[TODO](TODO.md)；这些都不是已完成的RAW预拍功能。

## HALF09/10：绑定原厂停止服务的等待缺口

HALF09保留HALF08输入，实际看到上层`B48c/800000`等待成功、随后的`B48c/80000`等待失败，取消来自原厂`40e90f0c`。最终半按观察窗口内未命中`B498/18000`，不能将它推定为本轮等待对象，也不能据此排除更早模式切换期间的执行。

HALF10进一步绑定实际实例：服务索引0、服务对象`a02f26460`、设备ID`1f9`、请求`a02920608`的`+70=1`，选择C0环形分支。停止请求前，`15431000`为active、control101、mask29、pending0。原厂软件flag2等待成功；C0随后进入inactive/control100，下层ANY-mask2c等待返回false/flags0，停止包装返回4。清理时再次等待失败，最终`42200021`报告结果4比上层80000等待失败晚492,998,438ns。操作前报告内已有旧值4，只有最后实际派发的报告用于本轮结果判定。寄存器状态取自暂停快照，未将快照时间当作每次MMIO写入的精确时间。

原厂`status+14 bit5 → IRQ6a → W1C → event41070030 → 40cb7200`为该请求提供flag4；80000是服务终结报告，失败也会产生，不是像素完成。新[默认关闭的C0停止确认模型](z8-1543-c0-stop.md)在既有同步像素写入停止后提供该设备状态原因，不改任务标志或结果，也不复用C1实际图像输出的bit5语义。22项实际QTest和原32项D980、29项F04F回归已通过。

HALF09/10仍未产生历史帧或RAW像素，释放半按后仍到达mode2/slot3资源缺项。上面定位与模型属于控制链补全，不表示内部Bayer供应、历史保留或RAW预拍已实现。

## HALF11：停止确认通过，像素链仍未完成

仅更换固定模型二进制、启用C0选项并增加只读状态后，原厂下层mask2c等待实际返回flags4，停止包装及终结报告均返回0，上层80000等待成功。4次C0停止均由原程序ACK，剩余所有权为零。这是控制链的动态验证，未产生D980帧或RAW字节。

本轮终结报告发生在释放半按之后，后续取消请求为bf00；HALF10则在释放前取消ff00，不能当成相同执行阶段。两轮原输入和UI动作配方相同，C15/RAW/PRE/0.3秒/Lossless门禁均核对，但实时ISO/测光显示存在差异，原因未判定。HALF11最后仍发生mode2→slot3=0原异常，未补该资源、未跳过异常。104项源与输入检查均保持一致，QEMU已停止；具体时间和边界见[C0模型记录](z8-1543-c0-stop.md)。

补充观察边界：HALF11的HSFC作业/D980配置约在134382198425ns建立，早于最终半按135498091538ns；13个停止观察点只在最终半按窗口启用。不能把窗口内未命中启动点解释为从未启动。半按期间名为`hsfc_frame_callback`的记录携带04270028，原`40f6e4a0`分支实际忽略该事件，没有据此证明数据入队。现有模型已输出预览图像，这也不等于Bayer历史供应。后续须从C15模式切换前观察真正的数据回调、stage等待及同一job的原池描述符。

## HALF12–14：真实半按边界与历史作业门控

这三轮沿用HALF11的a3b二进制、四字节实验NEF政策、slot15=1/slot3=0及96次原输入，最终保持半按2秒、释放后观察4秒，没有全按。它们改变的是私有只读观察器，未补内部Bayer源或伪造完成事件。MAIN及输入身份与前述政策对照一致。

HALF12在观察器参数校验处停止：共享等待函数还有type6的合法`0x80080000`分支，原假设的`0x80100000`并非覆盖全部调用。HALF13按完整分支条件验证后实际看到该type6调用，以及5个最终半按前的type11作业；4个配对type11等待用`0x80100000`，返回W0=1/flags=`0x32e000`。随后两个CPU同时命中已配对后继，观察器保留首错并停止，没有推定先后顺序；最终半按尚未发送。

HALF14为高频观察点保留前置4次、最终半按请求窗口12次额度，区分请求窗口和实际消费时间，并为独立已配对后继增加有界处理。43项测试在普通/优化模式均通过；实际运行没有触发多后继批处理分支。三个新截图核对为Lossless、0.3秒及C15/RAW L/PRE/FX/A/MF/ISO AUTO100。
