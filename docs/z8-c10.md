# Z8 C10 仿真扩容实验

本实验只针对固定的 Z8 C3.11 MAIN。原始输入只读；派生 MAIN、原固件片段、NAND 镜像和截图仅保存在本地研究目录，不构成相机升级包，不支持刷机。

原始 MAIN 的 SHA256 固定为 `2b43a31c9de838f84b12416de4348a7004e65be07f853ec56ec2b10f3a8e3853`。生成器只在新的输出目录创建派生文件，先核对输入身份、每处原字节及区间，再组合补丁；验收还会复核原始输入未改变。不同派生版本的运行证据不能相互替代。

## 实现范围

原照片/视频两组 Custom Picture Control 记录各扩展到十项，并保留视频跟随照片的来源关系。每个记录包含有效标记、设置键、原生转换后的 `0x114` 参数、`0x242` 附加数据，以及 Flexible Color 所需的44字节扩展参数。C10 的内部选择值分别为40和90，显示代码40；已有内置代码37、38、39不能占用。

原生数据链：

```text
实验文件输入服务 → 410adc64 解析 NP3
                → 410dac30 将 0x158 中间对象转换为 0x114 参数
                → 410ac6d0 解析附加数据
                → 41015ec0 原生设置写入
                → 独立的 C1…C10 记录
                → 410a7bcc / 410a7d84 选择
                → 410a7b58 / 410a7d10 原生当前设置读回
```

实验使用自行构造的0300基础NP3和0310 Flexible Color NP3。后者的非零参数由原 `410aea68 → 410af260` 解析，额外44字节保存在record+`0x370`，通过具有明确类型和长度的设置键与当前对象恢复。**真实云创/NX Studio导出文件、在线下载、真实SD卡导入和ISP颜色效果尚未验收**。扩容解决的是机内记录数量；云端账户、服务协议和设备授权不在此次实现中。

这里的“导入”指实验文件输入服务向原厂 NP3 解析器提供字节，再由 guest 提交设置记录。它没有完成相机“管理优化校准 / Manage Picture Control”中的文件浏览、从卡复制、重命名、删除或导出流程。下文的 LCD 适配针对“设定优化校准 / Set Picture Control”的选择页，不能据此宣称上述管理页面也已扩为十槽。

原来的九项循环不能直接改成十：缓存组相邻，第十项会撞到下一组；UI标签表只有九个半字，原生设置表还有其它类型的数据。实现使用独立数组，保留原生解析/转换/设置函数，对新组 `0x7c` 提供六个显式描述符（两组主参数、附加数据和Flexible Color扩展）。原九项iMenu构造后追加C10；原生列表入口另从owned records重建完整十字节有效位图，避免旧调用者只有九字节而越界。五个新标签ID经原厂 ASCII 字体链渲染独立的 `C-10` 文本。

## LCD选择页适配

`z8_picture_control_main_menu.py` 同时包含属性缓存/PTP元数据和实际LCD页面适配；两者使用不同的表与调用链。属性候选41项只表示31个内置项加10个自定义项，不包含LCD分隔符，也不能证明屏幕已经显示C10。照片GUI上下文1、视频上下文14，分别对应记录来源组0、1，不能直接把GUI上下文当存储组编号。

实际LCD适配复制每页原来的行定义与逐行事件指针表，保留C1至C9及其它行，再追加独立C10行。新事件表复制对应页面完整的C9事件结构，仅替换两个选择回调：照片调用原 `403f96a8(40)`；视频先通过原设置接口将 `0300122c` 清零以解除照片继承，再调用 `403f96a8(90)`。通用控件分配、按键分派和高层设置通知继续由原代码执行。

两份选择值/行键表扩为41项，名称、初始焦点、上下移动及再次选择都引用同一份表。查表容量只在访问这两份新表时从40增为41，其它GUI上下文保持原表与原容量。新增行使用独立行键，名称从对应原生参数对象读取；左侧编号选择专属 `C-10` 文本资源，不读取九项图标表后的相邻数据。创意图标的第十槽标记也有独立存储，并在控件池指针变化时清零。

编号文字使用该LCD页面的原生样式索引 `0x21f`，按原 `40695e3c` 的 `0…0x652` 样式表范围校验。样式索引不是8位字体编号；也不能从尚未初始化的动态文字槽推断有效样式。原生文字布局仍负责字号、位置、裁切与最终像素。

这些接线已有原A64函数与补丁契约测试，包括旧行/旧事件字节不变、原生焦点查找、两种选择回调和缓存隔离。测试中的控件或事务边界记录不等于LCD像素验证。只有新派生镜像上的真实MCU按键、原current/设置ID读回及截图审阅，才能确认可见、可选和重新进入后的高亮状态。

## 仿真内存与装载

| 区域 | 范围 | 用途 |
|---|---|---|
| RX | `45000000–45003fff` | 导入、选择、列表和保存/恢复入口 |
| RX | `45004000–45006fff` | 原生菜单扩容适配 |
| RX | `45007000–45007fff` | 原生文字资源适配 |
| RX | `45008000–45008fff` | guest A64 NAND 持久化 |
| RX | `45009000–4500bfff` | 主属性/菜单适配 |
| RW | `a116eb000–a1171cfff` | 设置描述符、记录和工作区 |
| RW | `a1171d000–a11722fff` | UI数组、状态和标签 |
| RW | `a11723000–a1172afff` | NAND头工作区与独立调用栈 |

这些地址是本仿真的实验区域，**不是实机空闲空间证明**。原厂启动会清理ROM/RAM间隙；在清理完成的 `4016e6a8` 检查点，通过原运行时 `40172b88` 添加窄范围RX及RW/NX映射，由原接口维护页表分配bitmap和TLB。启动前使用 `40161514` 的映射会被后续清理，不能采用。低地址区域实际是NOR ROM-device，普通QTest/GDB写入不等于ROM装载；由 `z8_c10_image.py` 校验全部原字节、生成独立派生MAIN并使用QEMU启动loader装入附加区域。高地址初始化数据补丁转换到原MAIN的对应scatter文件偏移。页表映射不等于物理内存分配。实验派生MAIN另将原 General heap 描述符大小从 `0xb00000` 缩为 `0xac0000`，明确保留其尾部256 KiB，保持相邻Heap的起点不变；运行时仍需核对原分配器采用的实际边界。原先的 `a07e00000` 位于Linux镜像加载区，已弃用。

实验函数调用会临时改寄存器；元数据明确记为主动实验。常规调用先等待真实MCU RX任务边界，核对TPIDR/TCB、IRQ和原锁条件；保持单CPU继续及原DAIF，使用独立栈。仅guest NAND操作内部短暂屏蔽IRQ/FIQ并恢复，启动MMU调用另行记录为早期屏蔽模式。结束恢复通用寄存器、向量寄存器、FPCR和FPSR；发生超时、未知MMIO或非预期停止均失败。不能把这种调用记作原厂正常任务调度验证。

## 保存与重启恢复

扩展记录通过guest自身的A64代码操作NAND寄存器。独立新实验镜像的最后两块作为A/B区，包含版本、原MAIN身份、世代和CRC。保存次序为另一块擦除、payload写入、header最后提交、读回验证。读取错误拒绝保存；旧副本不因一次失败写入而被替换。两块保留是实验布局，不能照搬到真实NAND。

schema2保存两组各十条记录，每条步长 `0x400`，其中 Flexible Color 的44字节扩展与主参数、附加数据一同持久化。头部同时保存两个当前目标的槽位及来源组；视频跟随照片时，视频目标可以恢复照片来源组的C10，而不会错误读取视频组的另一个C10。SAVE读取原current selector，因此切回C9会保存C9，切换内置项会清除扩展头部的当前自定义槽位，避免重启后恢复陈旧C10；内置项本身的保存仍属于原系统范围。

宿主提供持久化NAND模型、实验输入及启动编排，不把Python字典或上次RAM快照当恢复结果。恢复阶段必须启动新QEMU进程，从已有NAND镜像读取，并逐条比较前一次保存的独立哈希；参考哈希不写入guest。原guest LOAD恢复记录与当前对象后，启动编排按从NAND恢复的选择元数据调用原 `403f96a8 → 410d8060 → 410d95d8`，使设置ID和通知与当前对象一致；在 `40f25960` 只读观测真实 `04300001 / 40000410` 通知，并继续到原函数正常返回。

此实验从全新的隔离媒体开始，显式种入C1至C9回归样本。**已有真实机身设置迁移、原厂全部设置持久化、热断电和硬件NAND磨损均未验证。**

## 运行方法

使用本项目的Linux/WSL环境，安装 `requirements-c10.txt`，先构建包含可选持久化NAND的QEMU。原始MAIN路径遵循 `docs/firmware.md`；所有运行目录必须是新目录。

```sh
python tools/z8_c10_acceptance.py --firmware .local/firmware/z8-c311-main.bin \
  --qemu /path/to/qemu-system-aarch64 --phase create \
  --output /path/to/new-create-run --media /path/to/new-c10-nand.img --gui-test

python tools/z8_c10_acceptance.py --firmware .local/firmware/z8-c311-main.bin \
  --qemu /path/to/qemu-system-aarch64 --phase restore \
  --output /path/to/new-restore-run --media /path/to/new-c10-nand.img \
  --expected /path/to/new-create-run/expected-records.json --gui-test
```

`create`拒绝覆盖现有媒体；`restore`要求媒体已经存在。默认标准启动器仍采用原固件路径，C10实验需显式运行上述工具。

增加 `--gui-test` 可在该阶段的服务/媒体检查之后执行实际MCU照片选择页流程：核对MENU基准画面，进入选择页，选择C9，再选择C10并重新进入，读取原current与设置ID并保存原生截图。该流程不是SD卡导入操作，也不自动认证截图中的槽号字形。

这套已提供源码的C10命令覆盖导入、设置、保存恢复及照片主菜单；下文独立视频的历史验收使用了未随仓库发布的私有驱动，不能仅凭上述命令复现其全部按键流程。仓库现在另有 [`tools/z8_slots_acceptance.py`](../tools/z8_slots_acceptance.py)，提供 `--slots 32` 配合 `--gui photo`、`video`、`video-cold` 的完整入口，见 [C32运行说明](z8-c32.md)。它使用schema3、新编号和新的派生镜像，须从新实验媒体开始，不能加载C10的schema2媒体，也不能代替C10历史镜像的复验。`--slots 32` 与 `--slots 64` 两种容量均已完成各自的四阶段集成仿真，详见 C32/C64 说明和公开数值收据；这仍不能代替 C10 历史镜像的复验。

## 验收层次

函数级测试覆盖原A64解析、转换、原生设置、十项独立性、原生菜单构造、标签资源、损坏与失败保存。QTest测试覆盖持久化设备的页操作和新进程重新打开。它们分别验证函数和设备契约；整机导入/选择/跨进程恢复、真实GUI像素和按键操作另需运行证据，不能用单元测试数量替代。

最终运行状态与可复现结果见对应派生版本的 `result.json`。`c10_service_media_passed` 只表示该次服务/媒体阶段通过；`cold_restore_verified` 表示新进程恢复检查通过。后续GUI失败不会撤销前一阶段的字段，不能据此把整次运行判为通过。GUI结果还需检查 `c10_main_menu_acceptance.mcu_selection_verified`，并单独审阅截图的C10编号、名称和高亮；`selection_verified_visual_review_required` 明确表示尚需视觉审阅。缺少某层结果时，不得以旧版本记录或单元测试代替。

### 可选GPU回归的额外输入

[`tests/test_z8_graphics_empty.py`](../tests/test_z8_graphics_empty.py) 是独立的空路径GPU模型QTest，不属于上述C10命令的必需输入。除QEMU和用户提供的固定MAIN外，它还要求两份各96字节的私有运行时shader捕获（fill/stroke）以及对应捕获运行的结果JSON。测试会核对捕获长度、源码中记录的SHA256，以及结果JSON中的MAIN身份。仓库仅包含这些身份信息和测试逻辑，不包含shader字节、原厂截图或捕获结果文件，也不假定捕获是可直接从MAIN截取的固定片段。

因此，仅安装依赖并提供MAIN不能单独复现这项GPU回归；拥有符合上述来源条件的本地捕获后，才可使用其 `--fill-program`、`--stroke-program` 和 `--capture-result` 参数运行。该测试保持guest CPU停止，只验证GPU模型事务，不能替代原厂菜单像素、拍摄或ISP效果验收。
