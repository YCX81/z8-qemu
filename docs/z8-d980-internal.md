# Z8 D980 内部端口：仅接受启动的实验模型

`z8-d980-internal-start-model=on` 默认关闭，只允许在 Z8 模型创建时显式设置。它接受一个已观察到的内部端口配置，让原程序继续执行启动后的配置和等待逻辑；内部图像供应者仍未实现。它不提供 DMA、帧、传感器标记、D980 帧完成或由 D980 引起的 source/channel 通知，不将 `0xe0000000` 映射成 RAM，也不修改固件、CPU 或任务状态。

该开关依赖既有 D980 stream 模型及其前置条件，不能单独启用。原 RAM profile、地址转换与默认关闭行为保持原样。普通 RAW 的已有证据见[运行对照](z8-raw-runtime.md)；此开关不将该证据推广到 RAW 预拍。

## 精确接收条件

新分支只接受 `0x150c0008=0xff00` 的32位写入。既有 configured、latched、重复 active、reset、stop、提交和字段有效性检查继续生效。D980 必须已有提交，低20个字段均有效，28个 latched word 必须全部等于下表；`0x4000`、`0x7f00` 等其它启动组合不由新分支放行。

| 相对 `0x150d9800` 的偏移 | 值 |
|---|---|
| `0x000`, `0x004`, `0x008`, `0x010` | `1`, `0x102c0000`, `0x0ac40002`, `0` |
| `0x100`, `0x104`, `0x108`, `0x10c` | `7264`, `1`, `1`, `0` |
| `0x110`, `0x114`, `0x118`, `0x11c` | `1`, `0`, `3`, `0` |
| `0x120`, `0x128`, `0x130`, `0x138` | 各为 `0xe0000000` |
| `0x124`, `0x12c`, `0x134`, `0x13c` | 各为 `0` |
| `0x140` 至 `0x15c`，步长4 | 全部为 `0` |

这些是有界 MMIO 配置观察，不是原厂校准表。不能仅凭几何字段推定完整物理 ROI、像素编码或 D980 与其它处理器的直连关系。

为避免误用旧 RAM 帧，新分支还拒绝已有 D980 帧、字节、pending 结果、单帧 armed timer 或 prepared 状态。它保留这些真实状态，不清零来满足检查。接受启动仅设置显式 `waiting` 状态和控制启动计数，不推进 input epoch 或单帧准备计数。

## 后续状态与取消

周期和单帧接收入口在打包、标记、地址转换、RAM 写入及完成发布之前拒绝该内部 profile。单帧 arm、tick 和 mode 路径也单独限制。活动期间仅允许相同配置重新锁存；改变 RAM/internal 数据来源在任何 latch 改动前拒绝，须先经过原 stop/reset。

原独立 stop `0x4000` 及有界 reset 可以取消等待，保留既有 stop-done/stop IRQ 协议。停止通知与帧完成不同；整个机器的独立周期源中断也未关闭。组合 stop `0x401e` 仍要求真实单帧完成，不因新开关而伪造 epoch、帧或通知。停止后残留的旧 latch 不会阻止下一套普通 RAM 配置的原生 preparation。

只读 QOM 属性 `z8-d980-internal-state` 提供 `enabled`、`waiting`、`starts`、`control_cancels`、`blocked_inputs`，并始终声明 `supplier_implemented=false`。这些计数是控制与等待证据，不能当成已捕获帧。

## 验证与边界

32项真实 QTest 在普通与 `python -O` 模式下通过：默认关闭、错误机型、依赖、错误 profile、访问宽度、未观察过的启动掩码、重复启动、重新锁存、旧 prepared/armed/帧状态、停止/复位及后续 RAM 准备均有正反例。精确内部配置在实际虚拟定时器推进期间仍保持零 D980 像素、帧、标记和来源通知；普通 RAM 对照在开关关闭和开启时均产生预期2048字节帧。

测试只用自写空 kernel 和合成 Bayer 输入，通过不执行 CPU 指令的 QTest accelerator 操作 MMIO。为了实际触发定时器，测试短暂打开 VM 的定时运行状态，再暂停读取结果；这不是运行 Nikon 固件。测试驱动覆盖率为98.4%语句、88.5%分支，不代表 C 模型覆盖率或实体硬件验证。

```sh
python tests/test_z8_d980_internal.py --qemu /path/to/qemu-system-aarch64 --output /path/to/new-results
```

## 私有原程序对照06

该次研究运行保留05的原生 RAW/Lossless、C15、0.3秒预拍窗口及半按流程，并保留原有单指令派生格式策略和外部 selector15 输入；不是未修改固件的默认功能。私有驱动未作为公共完整复现入口发布。新增模型实际接受了 `0xff00` 启动，`waiting=true`、`starts=1`，一次周期输入被阻止；D980 字节、帧、pending、传感器标记和 RAW151 jobs 仍全部为0。

原程序随后在 `0x40c1fce4` 发出 `0x150c000c=0xf04f`，触发新的严格拒绝，未继续添加白名单或补造完成。共95次原生输入消费和返回全部匹配，没有 FULL，半按后的 release 尚未发送；26个只读 getter 的停止现场已保存，原始 MAIN、派生文件及运行源哈希不变，自有 QEMU 已停止。

需要区分首故障日志与暂停快照：`0xff00` 启动日志的 active 为 `0xff5f`；首个未知访问后、所有CPU实际停止前，原程序又执行了既有独立 stop `0x10`，暂停快照的 active 因而为 `0xff4f`。其 group0 stop pending 来自该控制取消，不能解释成 D980 帧完成。首故障现场是在清理前获取，不是未知指令执行前的原子快照。

这次对照仅证明能越过已知内部端口启动阻点并暴露下一个原生停止协议缺口。当前模型仍没有内部 FIFO 图像供应者，不证明高速拍摄、历史缓存、有效 NEF 或 RAW 预拍成功。
