## 构建与运行

QEMU 10.2.4 归档通过上游 SHA-256 检查，独立编译完成。`nikon-z8-bringup` 与原 `nikon-z9-lab` 分别注册。新增机器保留原模型的严格未知 MMIO 停机；实际硬件差异继续通过停止点调查。

| 实际 Z8 情景 | 停机 PC | 未实现访问 |
| --- | --- | --- |
| 默认 | `0x41187158` | CPU0 read `0x0d150000`，4 字节 |
| bootstrap | `0x41185c00` | CPU2 read `0x14154040`，8 字节 |
| bootstrap + bus-window | `0x40c14704` | CPU1 write `0x0e70073c`，4 字节，值 1 |
| bootstrap + bus-window + serial | `0x40c5e398` | CPU0 read `0x17800118`，4 字节 |

以上为第一轮严格模式停止点，保留作回归依据。当前显式启用 NAND fixture 后已执行页读取：原厂命令 `0x40302200` 将 page0 的 2072 字节传入原厂指定 RAM。模型使用空白虚拟 NAND，未恢复相机 NAND 实际内容。

新增 Z8 syscon 保留寄存器和有限存储控制位，另用默认关闭的 `z8-sd-empty-fixture` 表达无 SD 卡。相邻未知寄存器、非法宽度、保留位仍停止。Z9 默认路径保持原有行为。

`profiles/z8-c311-bindings.json` 固定 MCU 断点、IRQ 对象、串行对象及回调的 Z8 地址，拒绝其他 MAIN。原厂 TX/RX FIFO、校验和、GPIO ACK、镜头启动回调及最终 RX 退休均有实际执行证据。完整连续对照已记录 35 个 TX 与 4 个 RX 成功，后续较长运行继续增加；不等同物理 MCU 协议全部恢复。

## 缺失资源导致的初始化阻塞

原厂 Battery item `0x1c` 的 `+0x174` 是 GPIO 去抖采样次数，`+0x170` 是原定时器间隔。全零输入使 `0x40317f00` 的计数先减成 `0xffffffff`，执行约 42.95 亿次循环；其他初始化 worker 在屏障超时后继续推进，最终关闭中断，连带使 MCU ACK 不能完成。

Z8 原始初始化数据在文件偏移 `0x4b2080c/0x4b20810` 存有 interval20 与 mask15，原厂 DMA 确实将其搬入运行地址。`z8_resources.attach(native_sampling=True)` 用外部资源字段 interval20/count4，让原算法重建原有的掩码15。原厂函数自然执行到循环之后、运行值正确，phase3/phase4 全部 worker 的屏障返回成功；没有修改固件代码、CPU、任务状态或等待返回值。

这是从本机初始化状态推导的虚拟参数，不是恢复的工厂校准。其他 Group12 字段仍为空；ENDM 是原资源读取器所需的格式尾标记。Z9 Battery、TEMP 等借用对照未改善后续黑屏，未进入默认配置。

第二个阻塞来自电池保护：Z8 原厂启用 mode1，从 item1c `+e0/+e4` 读取两个保护阈值；全零资源使三个 signed-byte 样本0达到阈值0，原代码置故障并将 APPCTL 状态1转为4，继而向 RAW 发送关闭配置。Z9 对应 mode0 不启用这项检查，不能直接复用其空参数。

当前以原始 Z8 mode2 分支内的88/77作为明确标注的虚拟外部阈值，经相同 mode1 读取和比较：正例观测到阈值88/77、样本0、故障0、APPCTL状态1及原 RAW 入口参数1。没有改变模式、故障标志或比较分支；实际物理单位和机身校准值仍未知，也不将这两个数命名为滞回。详见 [电池资源来源](z8-battery-resources.md)。

## 本地运行入口

仓库根目录的 `Start-Z8.ps1` 启动 `tools/z8_run.py`，界面在 `http://127.0.0.1:8788/`。菜单与半按快门通过原厂 MCU 帧路径送入。界面只展示 QEMU 原帧缓冲，不绘制替代菜单。运行记录写入 WSL Linux 磁盘；对 `/mnt/c` 上持续增长日志曾观察到 ENODATA，因此长时间运行不使用 Windows 挂载目录作为输出盘。

`-Headless -Seconds 360 -MenuTest -RequireLiveView` 是菜单与模拟取景的有界验收命令；三轮 MENU 往返和扫描输出一致性检查必须通过。默认互动运行的 `-Seconds 0` 表示运行到手动停止，网页提供“停止仿真”。启动阶段同样支持取消，已实际验证停止接口在启动早期退出并清理自己创建的 QEMU。

## REA 结果与模型边界

REA/Ghidra 已实际分析两个来自原始 Z8 MAIN 的完整函数切片。两份 ELF 都明确标记为分析容器，并记录原载荷、切片和容器哈希；不是原厂 ELF，切片外数据没有载入 Ghidra。

1. `0x41187154`：读取 `0x0d150000` 高 4 bit，减一后限制到 4 bit，仅在归一化值小于 3 时写入 `0xa0497d1c4`。这是数据路径证据；寄存器真实上电值仍未知。Evidence ID：`ev_22ee6c6363c608c6e1dfa10693fb3539bb252add980e7bba9b79d6b91aa54865`。
2. `0x41185b94`：查询 `0x44b7d6ac` 端口表与 `0x44b7dcb4` 分组描述符，读取窗口起点、负长度和偏移。Evidence ID：`ev_666ebe35dea6704b67750aa7d0b5e3ffdcdace2a3215f9b189042c00b0d06f37`。

另外读取 Z8 的 17 组、每组 24 字节总线描述符，比对了两个窗口基址、两个控制基址以及有效槽数。paired 标志出现在 3/4/10 组，有效槽数为 `slot_count << paired`；这些软件寄存器布局与继承模型一致。该表 SHA-256 为 `f07fcbfdd7b322afcd91a9cd2522e4d4f7e986d165affb0728a2478f108c71a8`。

该比对没有恢复 Boot ROM/bootloader 设置的窗口初值。128/512 MiB 等初始窗口、SoC revision、FIFO 深度和部分 IRQ/时序继续属于 Z9 来源的实验假设，不能作为真实 Z8 参数使用。
