# Z8 C3.11：3D 遮挡响应隔离实验

2026-10-12。基于 `228a34c` 的独立工作树，分支 `codex/z8-af-lockon`。

**已定位真实 AF 资源的地址和加载链，已确认共享限幅的历史状态来源，并通过保留限幅的用户档位查表实验。真实 AF 参数块内容仍未恢复，不能宣称完成真实参数验证或改善了实机对焦。**

## 输入与范围

- 原始 MAIN：81,807,709 字节，SHA-256 `2b43a31c9de838f84b12416de4348a7004e65be07f853ec56ec2b10f3a8e3853`。
- 官方升级包：99,051,117 字节，SHA-256 `d67413c2ede6b9ce8887175f20700bd9fbad2a973a4820968c45503d15d80d96`。
- 使用原始 AArch64 指令和初始化数据，在 Unicorn 中执行有明确停止点的片段；程序映像页只读。初始状态及校准数据为显式合成输入。
- 候选只改变当前 Unicorn 实例的一项 RAM 分发表指针。没有修改寄存器结果、跳过被测判定或伪造函数返回值的 hook；hook 仅观察参数读取并在指定边界停止。
- 没有生成派生固件、修改默认 QEMU 启动器、运行完整 AF 闭环、访问实体相机或刷机。工作树外只读取已有固件与依赖。

## 真实参数所在位置

原始目录位于 MAIN 文件偏移 `0x4c27948`，条目长 `0x30`；组目录位于 `0x4c28ab8`，组长 `0x28`。原始访问器 `0x40d712c8` / `0x40d712ac` 与目录内容一致。

| 对象 | 已确认的地址或范围 |
| --- | --- |
| 资源组 `0x12` 的 ROM 视图 | `0x462e0000`，extent `0x20000` |
| AF 条目 `0x25` | 组内偏移 `0x10800`，长度 `0x2d00` |
| AF 条目原始地址 | `0x462f0800` |
| 算法参数基址 `P` | AF 条目 `+0xc04`，对应 ROM `0x462f1404` |
| 共享限幅使能 | `uint16(P+0x5c)`，对应 `0x462f1460` |
| 3D 专用门限表 | `uint16(P+0x80+2*i)`，起点 `0x462f1484` |
| 普通照片时间表 | `uint16(P+0xd0+2*i)`，起点 `0x462f14d4` |
| 特殊状态时间覆盖 | `uint16(P+0xd8)` |

执行原厂初始化前缀 `0x40d70dbc..0x40d70f88`，得到组缓冲 `0xa159a38c0`、AF 条目缓冲 `0xa159b40c0`。`0x40db29a8` 通过条目 getter 保存指针；`0x40db2a1c` 返回 `0xa159b4cc4`，即条目 `+0xc04`。这些是该初始化路径的地址结果，不是从实体相机读取的运行快照。

执行原厂资源读取器 `0x40d6c320`，获得两项有区分力的结果：

1. ROM 全为擦除值且无 `ENDM`：返回 0，目标缓冲保持预置哨兵值，未产生默认 AF 表。
2. 相同擦除值仅加末尾 `ENDM`：返回 1，把擦除内容复制到目标缓冲。

因此，**读入成功、条目指针非空、甚至有 `ENDM`，都不能证明参数有效。** 该读取路径在失败时调用的 `0x40d712a4` 只是返回 1，没有填充校准数据的实现。

本次重新解密并验证全部五个模块和升级包 CRC，在全部解密模块中扫描 AF 零填充标记、关联资源标记及已知参考时间序列，未找到可确认的 Z8 AF 原始块。该结论只覆盖原始字节签名搜索，**没有排除压缩、其他编码或未知布局**。也没有将 Z9 表复制过来冒充 Z8 数据。

## 共享限幅的具体条件

照片路径使用用户设置的零基索引 `i`。原始归一化把 1..5 映射到 0..4，无效 uint32 输入回退到 0。

```text
if history.previous_hold != 0 and uint16(P + 0x5c) != 0:
    i = min(i, 2)
```

这一判断出现在 `0x40e131a0..0x40e131c0`、`0x40e17a88..0x40e17aac`、`0x40e18010..0x40e18034` 三处，分别影响时间表、第一组门限表及后续上下限表。

`history.previous_hold` 已追到以下来源：

- `history = 0xa037dbbe0`；算法上下文 `0xa037df350+0x48` 指向它。
- `history+4/+5` 是当前状态，`+0xc/+0xd` 是上一轮状态；`0x40e1161c..0x40e11650` 按 8 字节槽移位，真实指令把 `+5` 复制到 `+0xd`。
- `0x40e1322c` 是当前 `+5` 的已确认置位点。只有照片路径且算法模式为 0/1 才会执行；3D 模式 8 跳过置位。
- 触发前还要求配置 `+0x10 != 0`、当前测量类型 `<=1`、测量绝对值低于 `P+0x126` 所定义门限，以及分类 getter `0x40db65c4` 返回 1；配置 `+0x7c` 必须允许该状态。当前 `+4` 带锁存，且上一轮 `+0xc==0` 才进入新触发分支。
- 已置位状态在原始计时差无符号比较达到 `0x259`（601）时清除；配置 `+0x7c==0` 或原厂重置函数 `0x40e11718` 也会清除。单位尚未实机测量。
- `0x40e11a50` 另有输出结构 `+0xd`，但它不是本限幅标志的直接写入来源，不能因为偏移相同就混为一谈。

保留原始指令的连续片段实验，在设置 5、合成限幅使能开启的条件下得到：

| 模式 / 内部时刻 | 当前 `+5` | 本轮读取的上一轮 `+0xd` | 候选使用的用户索引 |
| --- | --- | --- | --- |
| 模式 0 / 100，首次触发 | 1 | 0 | 4 |
| 切为 3D / 200 | 1 | 1 | 2 |
| 3D / 700，经过 600 单位 | 1 | 1 | 2 |
| 3D / 701，经过 601 单位 | 0 | 1 | 2 |
| 3D / 702，历史更新后 | 0 | 0 | 4 |

这证明**保留历史状态时**会有延续及一轮延迟。真实模式切换可能先调用重置，因此不能断言相机切换模式必然出现此现象。分类枚举 1 的摄影语义尚未完全命名；当前证据支持“带历史和超时的运行状态”，不支持把它简单叫作“遮挡检测”或“任意识别目标标志”。

## 隔离候选及影响范围

原始模式转换函数 `0x40e0dd60` 把照片区域值 5 映射到算法模式 8。候选仅在模拟内存中把分发表 `0xa029eb4a8` 从 `0x40e131fc` 改为 `0x40e132f4`。

- 原始 3D 路径保持 `W21=500`，跳过用户时间表。
- 候选执行现有 `P+0xd0+2*i` 查表，使用普通或调用拍摄功能后已经选定的有效用户设置。
- 三处共享限幅均保持原样。限幅未激活时，设置 1..5 使用索引 0..4；限幅激活时使用 0、1、2、2、2。
- 3D 专用门限 `P+0x80` 和上下限 `P+0xae/P+0xc2` 不变。
- 非 3D 模式及两条视频时间表路径，结果和观察到的参数读取相同。
- 配置 `+0x1a9` 特殊覆盖的最终结果不变。不过候选会先多读一次用户表，再被 `P+0xd8` 覆盖；不能称为执行轨迹完全相同。
- 该处时间门限还经过累计及缩放。500 不能直接解释为每次遮挡必定等待 500 ms。

实验明确使用 `1000 + 字节偏移/2` 的合成半字值来区分读取位置。示例中的 1104..1108 **不是 Z8 的真实响应时间**。没有测试全局取消限幅或修改目标识别模型的版本。

## 复现与验证

先安装可选 `requirements-af-probe.txt`；包审计还需仓库常规 NumPy 依赖及独立安装的 `nikon-fw-key-tool`。固件、密钥和完整结果均放在忽略的 `.local/`，不随源码发布。下列路径为示例，替换为自己持有的输入位置：

```powershell
python -B tools/z8_af_resource_audit.py --package .local/firmware/Z_8_0311.bin --decoder ../nikon-fw-key-tool/decrypt_firmware.py --key .local/firmware/xor-key.json --output .local/af/package-audit.json
python -B tools/z8_af_lockon_probe.py --firmware .local/firmware/z8-c311-main.bin --output .local/af/probe.json
python -O -B tools/z8_af_lockon_probe.py --firmware .local/firmware/z8-c311-main.bin --output .local/af/probe-optimized.json
```

已有输出会被拒绝覆盖；错误版本、升级容器或派生 MAIN 不能通过身份检查。验证用显式异常，不依赖 `assert`。普通模式与 `python -O` 的结构化输出逐项相同。

## 只有官方升级包时的追加检查

用户确认目前只有官方包后，搜索扩展到标准压缩数据和 `li2070_0311b0.bi` 的 NISI 分区，未找到可确认的原厂 AF 参数块。

- 在全部五个模块扫描带格式头的 zlib、gzip、bzip2、XZ；单流默认输入、输出各限制为 2 MiB。只把到达流尾且校验通过的结果算作完整解码，记录超过上限或需字典的候选。
- MAIN 中完整解码 6,192 个 zlib 流，其中 6,187 个所在的 PNG IDAT 块 CRC 也通过。唯一 `AF` 零填充标记命中位于 MAIN 偏移 `0x2ef2439` 的 PNG IDAT 解压结果中，属于图像数据，不是原厂 AF 参数块。
- NISI 头声明 4 个分区，分别识别到 ARM64 Linux Image 头、gzip、两个带匹配长度的设备树头。目录块大小 `0x800` 与原始加载器 `0x41187bd8` 中“块数乘 4、每小块 512 字节”的读取方式一致。
- 依据 NISI 目录声明的长度，把偏移 `0x5b1000` 的 gzip 单独完整解码：压缩长度 9,846,203 字节，展开为 23,337,472 字节的 cpio；此步骤另设 128 MiB 输出上限。完整解析 821 条记录（820 个文件/目录等条目及一个结束记录），末尾剩余内容全零。全过程只在内存解析，没有挂载、创建归档路径或执行其中程序。
- cpio 中另一处 `AF` 命中位于 `cfg80211.ko` 的 ELF `.symtab`，文件偏移 `0x49cf8`，是符号值 `0x4641` 的小端字节 `41 46`，也不是 AF 参数头。

追加的 11 项无固件测试在普通和 `python -O` 模式均通过，覆盖嵌套 NISI/gzip/cpio 命中、校验损坏、输出上限、截断、分区重叠和未处理格式提示。原先 1,311 项 AF 指令实验没有改动，也没有因追加搜索而提升为真实参数验证。
