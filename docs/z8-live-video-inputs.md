# Z8 录像前置输入：RTC 与录制处理资源

2026-10-14。适用固定 C3.11 MAIN SHA256 `2b43a31c9de838f84b12416de4348a7004e65be07f853ec56ec2b10f3a8e3853`。所有输入均为显式仿真假设，不是捕获的 MCU 流量、恢复的工厂标定或实体录像验收。

## RTC 阻塞的证据与修复

`live-bitmap10` 在原厂 `40fd8754 → 40fd8670` 观察到133位活动位图中仅置位37、50、77。原算法复制允许检查的掩码，再排除13个 ID：77、78、48、49、50、53、4、11、20、21、23、26、103。原 `40fd7060` 求交返回1，取反后的许可返回0；最终交集仅剩37。

位37由原初始化 `40fa82d4` 设置。原 DateTime 通知 `43100003` 路径经 `40fc390c` 处理非零状态后，由 `40fc3958 → 40fd7b6c` 清除。该状态来自 `40cc7578` 的 DateTime 任务；静态字符串 `DtTm_MX1` 与日历换算代码独立支持其日期时间身份，不能将它误称为编码器完成标志。

原 MCU 路由表 `440c2178` 将第7路接到 `40cc85f0`；接收解码分派 `4101a110` 的线类型1调用 `4101a15c`，输出逻辑类型3和日期时间结构，再由 `40cc8040` 消费。

新模块 [`z8_datetime.py`](../tools/z8_datetime.py) 生成14字节载荷：

| 字段 | 线偏移 | 原解码器行为 |
|---|---|---|
| 类型 | 0 | 1，输出逻辑类型3 |
| 年 | 4 | 加2000，存16位 |
| 月、日 | 5、6 | 分别加1 |
| 时、分、秒 | 7、8、9 | 直接存入日期时间结构 |
| 状态枚举 | 12 | 本工具仅接纳0/1；原解码器输出1/2 |
| 状态枚举 | 13 | 本工具仅接纳0/1/2；原解码器输出1/2/3 |

1–3、10–11保持零。两个状态字段的完整物理意义没有确认，因此保留偏移名称，不给它们编造电池、校准或硬件健康名称。日期必须有效、无时区信息且精确到秒，年范围2000–2255仅表示当前字节编码的范围。

显式调用示例（在已拥有的 Z8 仿真 MCU Peer 内）：

```python
from datetime import datetime
from z8_datetime import rtc_body
peer.enqueue_external(rtc_body(datetime(2026, 10, 14, 12, 0, 0)), 7)
```

这是固定的本地时间测试夹具，不修改宿主时钟。默认启动和其他机型不自动注入；Peer 在入队前验证 MAIN 身份、长度、保留字节、日期范围和枚举，再复用原有串行/GPIO接收握手。

`live-rtc11` 实际通过原解码、DateTime任务和事件消费者；native date 为2026-10-14 12:00:00，两个状态word均为1，录像侧 `a03bc7b38` 由0变1，原程序执行清除37的调用。没有写录像许可位图、任务标志或 CPU 返回值。

## 新暴露的录制资源索引

RTC补齐后，`live-rtc11` 到达原异常：保存 ELR=`41170d84`，selector=10，原基址=`a155d78c0`；索引字节为0，原 `sub w14,w14,#1` 使其变成 `ffffffff`，形成错误基址 `2a155d78a0`。异常处理器后续读 `15080014` 的UNKNOWN属于收尾诊断，并非首因；失败记录保留。

既有外部资源只覆盖索引0、1、16。原资源ID `5c` 经 `40d6b4f4 → 411540f4 → 41166d54` 设置处理表基址。新增 [`attach_recording_processing_index()`](../tools/z8_video_resources.py) 为独立、默认不调用的实验，仅在外部 ROM 地址 `47f5af4a` 放一个字节1，选择同一中性记录，不改加载后的 RAM 实例。

`live-rtc-resource12` 已观察到原处理表位于 RAM，selector16与selector10均由原 `41170d5c` 读到1；下溢异常未再出现。该结果证明输入传到原读取链，**不证明缺失的 Nikon 图像处理系数正确**。

随后遇到新的原驱动访问：`40c2d90c` 写 `0d154248=00800000`。原复位表 `4164c494` 的ID `4a` 为 `{8,23}`，对应外设复位释放请求。新增有界模型仅在显式 Z8 视频接口实验下保留该请求，支持配对的保持请求和现有读回，拒绝混合位/错误宽度；该外设没有已接纳的工作，模型不产生DMA、完成IRQ或就绪状态，也不重置上游C1缓冲。未来加入此单元的数据处理时必须补齐实际所有权/复位语义。

`live-reset13` 通过ID4a后，原驱动接着请求ID4b `{8,24}`，写同一寄存器 `01000000`。按相同边界加入第二个独立锁存；不接受同时置23/24两位的未观察组合。最终 `live-reset14` 已通过二者，停于 `40c37114` 写 `16018000=0`。原 C3.11 `40c370f8` 随后还应写 `16018008=111`，属于视频处理控制初始化。参考项目存在 `video_processing_config_access`，但本工作树尚未移植/验证该模型，不能用固定读数或假完成跳过。

最终独立构建 SHA256：`ada1e556ccd400a74bfea76814c7260f811de3bffa5a618f65a9d340babf95a0`；上一版仅ID4a构建 `d730ea550ec4d0eca359d70711893a23ea574eb5f9a9394e1cb5fcc81263e5c2` 已冻结保存。原基线 `72971150...` 仍保留。

- RTC模块按先失败后实现验证，5项测试包含18组原始A64解码组合、闰日/日期范围、无效载荷、固件身份和实际帧校验和；原指令无替换。

- 复位ID74的旧候选测试确实失败；独立新构建后5组设备测试通过。C1 7组、第四路6组、视频接口20组相邻回归通过。初版“其他机型”负例未考虑已有构造阶段拒绝，修正测试为接受明确的Z8-only错误后通过，未放宽模型。
- 加入ID75同样先复现失败；最终构建6组复位、7组C1、6组第四路和20组相邻视频接口测试均通过，共39组。两个单元的读回/保持、请求计数和相互隔离都有实际QTest覆盖。
- `live-rtc11`、`live-rtc-resource12`、`live-reset13`、`live-reset14` 均已停止，MAIN哈希保持不变；各自停止后的虚拟卡 `fsck.exfat -n` 通过，仍是4目录和1个512字节管理文件，没有录像文件。
